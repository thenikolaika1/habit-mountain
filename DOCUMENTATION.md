# Habit Mountain — техническая документация

Справочник по текущему устройству приложения: как работает каждый
раздел, откуда берутся числа на экране, где что хранится. Описывает
**состояние проекта на сегодня**, а не историю его создания — история
изменений по заходам ведётся отдельно в `PROGRESS.md`.

Habit Mountain — трекер привычек: чистый vanilla JS (ES-модули, без
фреймворков и сборщика), hash-роутинг, вся логика — чистые функции над
одним объектом состояния в `localStorage`. Экран перерисовывается
целиком на каждое изменение состояния (`subscribe(render)` в
`js/app.js`) — отдельного вирт-DOM нет, каждый `renderXxxView()`
просто заново строит `innerHTML` (кроме экрана «Прогресс», который
патчит существующий SVG точечно — см. раздел 3).

## 1. Испытания

**Файлы:** `js/logic/challenges.js`, `js/views/challengesView.js`.

### Пул и активная пятёрка

Все возможные испытания лежат в одном фиксированном пуле —
`CHALLENGE_POOL`, 11 штук. Каждое — объект вида:

```js
{ id, title, description, icon, difficulty, check(m), progress(m) }
```

где `m` — помесячная статистика месяца, `computeMonthStats()` из
`js/logic/progress.js` (см. раздел 3): дни месяца с флагами
«зачтён»/«идеален», лучшие серии подряд, сумма отметок и т.д.

Каждый месяц **активны ровно 5** испытаний из 11 — выбираются
функцией `pickMonthlyChallenges(monthKey)`:

- Строка месяца (`"2026-08"`) хешируется (djb2) и превращается в
  сид для детерминированного PRNG (mulberry32) — значит, один и тот
  же месяц **всегда** даёт один и тот же набор, а вычисляется это
  каждый раз заново, налету, ничего не хранится.
- Набор набирается **не** сплошной перетасовкой всего пула, а
  раздельно по уровням сложности, с фиксированной квотой
  `TIER_COUNTS = { easy: 2, medium: 2, hard: 1 }` — это гарантирует,
  что каждый месяц вы увидите ровно 2 лёгких + 2 средних + 1 сложное,
  а не «два сложных и ни одного лёгкого» по случайности чистой
  перетасовки.

### Сложность

`DIFFICULTY_META = { easy: "Легко", medium: "Средне", hard: "Сложно" }`
— у каждого уровня своя цветная точка на бейдже карточки, но цвета —
это уже существующие токены палитры (`--color-accent` / `--color-warning`
/ `--color-danger`), новых цветов ради сложности не заводили.

### Прогресс в процентах

`getChallengeProgress(challenge, monthStats)`:

- если `challenge.check(monthStats)` уже истинно — сразу `1` (100%);
- иначе — `challenge.progress(monthStats)`, зажатое в `[0, 1]`.

`progress()` у каждого испытания — та же формула, что и порог в
`check()`, только выраженная как дробь до цели (например,
`bestCountedStreak / 5` для испытания «нужно 5 дней подряд»), поэтому
кольцо прогресса на активной карточке всегда доходит ровно до 100% в
момент, когда `check()` реально становится true — они специально
согласованы вручную для каждого испытания, а не выводятся друг из
друга автоматически.

### Медали

5 активных испытаний месяца получают 5 реальных фото-медалей
(`assets/habits/medal_*.png`) — `getMedalForChallenge(id, monthKey)`:

- для августа 2026 (`CURATED_MEDAL_MONTH_KEY`) награды подобраны
  вручную по смыслу названия испытания (таблица
  `CURATED_MEDAL_BY_CHALLENGE_ID` прямо в коде);
- для любого другого месяца (прошлого или будущего) — своя
  детерминированная перетасовка тех же 5 файлов, с отдельным сидом
  (`monthKey:medal`, не совпадает с сидом отбора самих испытаний),
  без повторов внутри месяца. Ручной подбор при смене месяца не
  нужен — новый месяц просто получает новую псевдослучайную, но
  стабильную раскладку.
- Если файл фото не грузится — карточка тихо переключается на
  нарисованную SVG-сцену (`wirePhotoFallback()`).

### Привязка к месяцу и «сброс»

Физически ничего не сбрасывается — само понятие «активные испытания
этого месяца» **всегда пересчитывается заново** по формуле выше, при
каждом рендере. Что действительно сохраняется в `localStorage`:

- `state.meta.completedChallenges[id] = { unlockedAt, monthKey }` —
  испытание, которое реально прошли (в любом месяце, не обязательно
  текущем) — one-way ratchet: одна и та же запись никогда не
  перезаписывается, `evaluateAndUnlockChallenges()` проверяет только
  ещё не пройденные;
- `state.meta.incompleteChallenges[id] = { monthKey, progress, endedAt }`
  — испытание, месяц которого закончился, а условие так и не
  выполнилось — записывается функцией `archiveEndedMonthChallenges()`,
  которая вызывается из `js/components/monthRecap.js` в момент, когда
  приложение впервые открывают в новом календарном месяце (сравнение
  `meta.lastSeenMonth` с текущим). Эта же функция **дозачитывает**
  испытания, которые формально выполнились в последние дни месяца, но
  приложение не открывали, чтобы поймать это вживую — ничего не
  теряется, даже если пользователь не заходил в конец месяца.
- Испытание, однажды провалившее месяц, но потом всё же пройденное в
  другом — запись в `incompleteChallenges` для него удаляется, в
  «Достижениях» остаётся только как пройденное.

Обе карточки — пройденные и незавершённые — показываются в разделе
«Достижения» (см. раздел 4), не в самих «Испытаниях» (там только
активная пятёрка текущего месяца).

## 2. Привычки

**Файлы:** `js/views/habitsView.js`, `js/state/habits.js`,
`js/logic/categories.js`, `js/logic/habitIconTopics.js`,
`js/logic/units.js`, `js/logic/completion.js`, `js/views/calendarView.js`,
`js/views/dayDetailView.js`.

### Типы привычек

Два типа, выбираются при создании и больше не меняются местами
(смена типа задним числом не предусмотрена формой):

- **Простая** (`boolean`) — отмечается галочкой, значение в
  `entries` — просто `true`/отсутствие ключа.
- **Числовая** (`numeric`) — значение либо одно число, либо массив
  чисел-«подходов» (см. ниже). `isDayComplete()`/`getNumericTotal()`
  в `js/logic/completion.js` — общая точка входа: день «выполнен»,
  если сумма > 0.

### Подходы (сеты) для числовых привычек

В попапе дня (`dayDetailView.js`) у числовой привычки два режима,
переключаемых на лету, без потери введённого:

- **«Одно число»** — обычный степпер (± и поле ввода).
- **«По подходам»** — список отдельных чисел («Подход 1», «Подход
  2», …), можно добавлять/удалять/редактировать каждый, итог
  считается суммой на лету.

Какой режим показать при открытии — определяется автоматически по
тому, что уже сохранено: массив в `entries` → режим «по подходам»,
число или пусто → «одно число». Хранится всегда только итог/массив —
отдельного поля «в каком режиме ввели» нет.

### Единицы измерения

`js/logic/units.js`: фиксированный список `UNITS` (раз, минуты, часы,
страницы, км, литры, подходы, калории, мл, шагов) + по эмодзи-иконке
на каждую (`UNIT_ICONS`) — свободный ввод текста не предусмотрен,
только выбор из списка, чтобы не плодить варианты вроде «мин»/«минут»/
«минуты». Единица по умолчанию для новой числовой привычки берётся из
Настроек (`meta.settings.defaultUnit`).

### Автоматический подбор фото по названию

Форма добавления/редактирования привычки **не** даёт выбрать ни фото,
ни иконку вручную — только имя и тип. Всё решает
`heroIllustrationForHabit(habit)` (`js/illustrations.js`) в три
уровня (подробности и полные таблицы файлов — в
`assets/habits/README.md`, ниже — суть):

1. **По эмодзи** (`PHOTO_BY_EMOJI`) — только для 6 пресетов
   «Популярные привычки» (Пить воду 💧, Чтение 📚, Медитация 🧘,
   Отжимания 💪, Сон 🛌, Прогулка 🏃), у которых иконка задана
   напрямую в коде, в обход формы. Привычка с таким же именем,
   созданная вручную через форму, тоже получит своё фото — совпадение
   идёт по эмодзи, не по тому, откуда привычка создана.
2. **По категории, определённой из названия** — основной путь для
   всего, что создано через форму. `detectCategory(name)`
   (`js/logic/categories.js`) — скоринг по вхождению ключевых слов
   (регистронезависимо, по подстроке) в 8 категорий (Спорт,
   Ментальное здоровье, Здоровье, Продуктивность, Обучение и
   развитие, Финансы, Дом и быт, Отношения), побеждает категория с
   наибольшим числом совпавших ключевых слов (не первая попавшаяся);
   при ничьей — та, что раньше объявлена в массиве. Если вообще
   ничего не совпало — `NEUTRAL_CATEGORY_ID = "productivity"`
   (Продуктивность) как разумный нейтральный дефолт.
3. **Нарисованная SVG-сцена** — если файл фото не найден/не
   загрузился, `wirePhotoFallback()` подменяет `<img>` на тематическую
   отрисованную сцену (для Спорта/Ментального здоровья — свои,
   `heroFitness()`/`heroMindfulness()`, для остальных — общий
   `heroDefault()`). Карточка никогда не остаётся со сломанной
   картинкой.

То же фото используется в списке привычек, в карточках «Популярные
привычки» и в шапке экрана привычки — везде одна и та же функция.

Отдельно, для мелкой круглой иконки рядом с привычкой в блоке
«Сегодня» на «Прогресс» — свой, более гранулярный скоринг:
`pickHabitIconTopic(name)` (`js/logic/habitIconTopics.js`), 18 тем
вместо 8 категорий (например, «Пить воду» и «Витамины» в
`categories.js` попадут в одну общую категорию «Здоровье», а здесь
получат разные иконки — капля воды и таблетка).

### Календарь

Два разных календаря в приложении, не путать:

- **В «Привычки» → экран привычки** (`calendarView.js`) —
  вертикальный список дней месяца (не сетка), каждый день — своя
  строка с числом, днём недели, статус-кольцом и (для числовых)
  суммой за день. Переключение месяца — стрелками в шапке или свайпом
  влево/вправо (`wireSwipe()`, порог 40px и угол не круче ~34° от
  горизонтали). Позиция (какой месяц открыт) запоминается per-habit
  на время сессии (`viewMonthByHabit`, не персистится в
  `localStorage`). При первом открытии экрана — автоскролл к
  сегодняшнему дню.
- **В «Прогресс»** (`mountainView.js`) — настоящая 7-колоночная
  сетка (`buildMonthGrid()`, понедельник первым днём недели,
  паддинг пустыми ячейками по краям) — см. раздел 3.

### Ограничение редактирования дней

Редактировать/отмечать привычку можно только за **сегодня, вчера и
позавчера** (`EDITABLE_WINDOW_DAYS = 3`, `js/logic/dateUtils.js`):

```js
export function editableDateRange() {
  const tKey = todayKey();
  return { minKey: addDaysToKey(tKey, -(EDITABLE_WINDOW_DAYS - 1)), maxKey: tKey };
}
export function isDateEditable(dateKey) {
  const { minKey, maxKey } = editableDateRange();
  return dateKey >= minKey && dateKey <= maxKey;
}
```

Проверка двухуровневая:

1. **Шлюз записи** — `isDateEditable()` в `dateUtils.js`, единственный
   вызывающий — `js/state/entries.js`'s `setEntry()` (реальная
   защита: даже прямой вызов мимо UI не пройдёт).
2. **UI-блокировка** — `calendarView.js`'s `dayPillHtml()`: день вне
   окна получает `disabled`, класс `.is-locked` и «залоченное»
   состояние кольца.

```js
// calendarView.js's dayPillHtml()
const locked = cell.isFuture || cell.isTooOld;
```

Раньше это ограничение на время было обойдено (для наполнения тестовых
данных за прошлые/будущие даты — `isDateEditable()` временно жёстко
возвращала `true`, а `dayPillHtml()` — `const locked = false;`), но на
данный момент оно снова включено и действует как описано выше.

## 3. Прогресс

**Файлы:** `js/views/mountainView.js`, `js/logic/progress.js`,
`js/mountainSvg.js`, `js/logic/points.js`, `js/logic/streaks.js`.

### Условие «дня, засчитанного горе»

`computeMonthDayResults(year, month, habits, entriesByHabit)`
(`js/logic/progress.js`) проходит по каждому дню месяца ровно один
раз и решает для каждого дня:

- `counted` — засчитан ли день горе: `completedCount >
  habits.length / 2`, то есть строго **больше половины** активных
  привычек выполнено в этот день (не «половина и больше» — именно
  строго больше);
- `perfect` — выполнены ли **все** привычки в этот день (более
  жёсткий бар, используется для достижения «Идеальный день»/
  испытания «Безупречный месяц»).

`computeMonthMountainProgress()` = число засчитанных дней / всего
дней в месяце (целочисленное деление в конце, а не накопление дробей
по одной — чтобы полностью пройденный месяц не срывался на
0.999999999 из-за погрешности плавающей точки).

Будущие дни месяца просто не имеют записей — они не в счёт, пока не
наступят и не будут прожиты; никакого специального кейса для «будущее»
в формуле нет, это просто естественное следствие отсутствия данных.

### Сброс каждый месяц

Гора никогда не копит прогресс «на будущее» — процент всегда
считается **для конкретного месяца** (`computeMonthMountainProgress(year,
month, ...)` принимает месяц явным параметром). 1-го числа условие
пересчитывается для нового месяца и естественным образом даёт 0%,
поскольку у нового месяца ещё нет прожитых зачтённых дней — никакого
отдельного «обнуления» не происходит, просто меняется, для какого
месяца идёт расчёт.

### Листание месяцев (уже реализовано)

Стрелки ‹ › рядом с заголовком «Гора за {месяц}» — `viewedMonth`,
модульная переменная в `mountainView.js` (не персистится, живёт на
время сессии, переживает уход на другую вкладку и обратно). Вперёд —
не дальше текущего месяца (`clampToNotFuture()`, защита и на уровне
рендера, не только у самой кнопки — кнопка «→» дополнительно
дизейблится). Клик по стрелке пересчитывает `computeMonthMountainProgress`/
`computeMonthStats` для нового `viewedMonth` и перерисовывает
гору/календарь/шапку статистики.

**Архивных данных как отдельной структуры нет.** Что бы вы ни
просматривали — текущий месяц или любой прошлый — это всегда одно и
то же чтение `state.entries[habitId][dateKey]`, которое хранится
бессрочно и никогда никуда не переносится/не архивируется отдельно
(см. раздел 7). Листание месяцев — это просто другой параметр `(year,
month)` в тех же самых чистых функциях.

### Чекпоинты на горе

`MILESTONES` в `js/mountainSvg.js` — 5 отметок вдоль тропы:

| % | Подпись |
|---|---|
| 10% | «Первые шаги» |
| 35% | «Продолжай!» |
| 60% | «Половина пути уже пройдена!» |
| 85% | «Ты почти сделал это!» |
| 100% | «Success» (флаг на вершине) |

Отдельно — «стадии» горы для подписи под кольцом прогресса
(`stageForProgress()`, `progress.js`): Подножие (0%) → Лес (25%) →
Скалы (55%) → Вершина (85%+).

### Блок «Сегодня»

Показывает **только сегодняшний день** — не зависит от того, какой
месяц листается выше в календаре. Список привычек с чекбоксом
(простые) или полем ввода (числовые), с анимацией «только что
отмечено» — `previouslyDoneToday`/`previouslyDoneForKey` diffing:
сравнение «что было выполнено на начало текущей синхронной пачки
рендеров» со «что выполнено сейчас», обновление базовой точки сравнения
отложено на `queueMicrotask()`, чтобы несколько рендеров подряд в
одном тике (например, отметка привычки + попутная разблокировка
достижения) не путали друг друга.

### Блок «Календарь месяца»

7-колоночная сетка (`buildMonthGrid()`) под горой, показывает
**просматриваемый** месяц (тот же `viewedMonth`, что и у горы выше).
Клик по дню → `openDaySummary()` (`js/views/daySummaryView.js`) —
всегда **только для чтения** сводка по всем активным привычкам за
этот день, вне зависимости от того, текущий это месяц или архивный —
никакого режима редактирования там нет вообще, попап просто
показывает, что было отмечено.

### Откуда берутся числа в шапке

Все три цифры в верхней плашке сейчас **помесячные** (относятся к
тому месяцу, что просматривается, а не пожизненные тоталы):

- **Очки** — `computeMonthStats(...).totalMarks × 10` (`POINTS_PER_DAY`,
  экспортируется из `js/logic/points.js`) — простая сумма отметок
  внутри просматриваемого месяца × 10, не полная пожизненная формула
  с бонусами за стрик (та не бьётся по месяцам корректно, т.к. бонус
  можно получить в середине пробега, который сам может пересекать
  границу месяца).
- **Общий стрик** — не «лучший пробег внутри месяца» (это обрезало бы
  реально текущий стрик, начавшийся в прошлом месяце, до куцего
  числа), а «каким он был на конец просматриваемого месяца» —
  `computeOverallCurrentStreak(habits, entriesByHabit, asOfKey)`
  (`js/logic/streaks.js`), где `asOfKey` — последний день
  просматриваемого месяца, а для ТЕКУЩЕГО месяца — просто
  `todayKey()` (поведение и число не отличаются от того, что было бы
  без листания месяцев). Это стрик **по всем активным привычкам
  одновременно** («каждый день были выполнены абсолютно все
  привычки») — более строгий критерий, чем «зачтённый горе день»
  (тот требует лишь больше половины).
- **% подножие** — `computeMonthMountainProgress()` того же
  просматриваемого месяца + `stageForProgress()` для подписи стадии.

## 4. Достижения

**Файлы:** `js/views/achievementsView.js`, `js/logic/achievements.js`,
`js/logic/challenges.js` (общие типы/структуры).

На экране «Достижения» — **два независимых источника данных**, оба
показываются карточками одного визуального вида
(`.achievement-tile` — компактная строка: маленькая медаль/эмодзи +
название + дата получения, клик открывает попап с подробностями), но
логика их получения совсем разная.

### 4.1. Особые достижения (долгосрочные, `ACHIEVEMENTS`)

`js/logic/achievements.js` — фиксированный список, сейчас 9 штук:

| id | Название | Условие |
|---|---|---|
| `first_step` | Первый шаг | Хотя бы 1 выполненный день-привычка за всю историю |
| `streak_7` | Неделя силы | Стрик 7 дней подряд по одной привычке |
| `streak_30` | Месяц дисциплины | Стрик 30 дней подряд по одной привычке |
| `combo_day` | Идеальный день | Все привычки выполнены в один день (от 3 привычек) |
| `combo_week` | Идеальная неделя | 7 дней подряд — абсолютно все привычки |
| `fifty_marks` | Полтинник | 50 выполненных дней-привычек суммарно |
| `hundred_club` | Сто отметок | 100 выполненных дней-привычек суммарно |
| `streak_100` | Сто дней силы | Стрик 100 дней подряд по одной привычке |
| `summit` | Покоритель вершины | Гора текущего месяца дошла до 100% (разблокируется один раз за всю жизнь приложения, не переоценивается каждый месяц) |

Ключевое отличие от испытаний — эти условия проверяются по **всей
истории привычки** (`bestStreakOverall`/`totalCompletedDays` в
`computeAppStats()`, `js/logic/progress.js`, сканируют от даты
создания привычки до сегодня), **без** привязки к месяцу и без
сброса — если стрик перевалил через границу месяца, он как считался,
так и продолжает считаться.

Разблокировка — one-way ratchet, `evaluateAndUnlock(stats)`: однажды
полученное достижение никогда не отбирается назад, даже если условие
позже перестало выполняться (например, стрик прервался). Хранится в
`state.meta.unlockedAchievements[id] = { unlockedAt }`.

### 4.2. Пройденные испытания (`CHALLENGE_POOL`)

См. раздел 1 — карточки завершённых месячных испытаний
(`state.meta.completedChallenges`) и отдельно, ниже — незавершённые
попытки (`state.meta.incompleteChallenges`, показываются с прогресс-
баром вместо даты получения).

### Когда именно засчитывается

Оценка (`evaluateAndUnlock()`/`evaluateAndUnlockChallenges()`)
происходит внутри `getAppStats()` (`js/state/derive.js`), которая
вызывается на каждый рендер экранов «Прогресс» и «Испытания» — и
**также на экране «Достижения»**: экран сам вызывает `getAppStats()`
в начале рендера исключительно ради этого побочного эффекта (сам
экран использует только уже готовые
`getCompletedChallengesMap()`/`getIncompleteChallengesMap()`/
`getUnlockedMap()` — чистые читатели состояния). Без этого свежая
разблокировка могла бы не попасть в `localStorage` вовремя, если
пользователь открыл «Достижения» первым экраном за сессию, минуя
«Прогресс»/«Испытания».

### Карточки и попапы

- `.achievement-tile` — единый компактный компонент и для особых
  достижений, и для испытаний. Медаль в кружке: у испытаний — реальное
  фото награды (`challengeHeroForId`/`getMedalForChallenge`, см.
  раздел 1) или SVG-сцена, у особых достижений — просто своя эмодзи
  на зелёном градиентном фоне (`.achievement-tile-medal--icon`) — у
  них нет понятия «месяц», под которое можно было бы подобрать фото.
- Клик → попап (`openModal()`): заголовок, описание, дата получения.
  У испытаний дополнительно бейдж сложности
  (`.challenge-difficulty-badge--standalone` — вариант бейджа без
  фото под ним, у оригинального бейджа непрозрачный белый фон
  специально рассчитан на фото-подложку и плохо смотрелся бы на
  плоской поверхности попапа в тёмной теме). У особых достижений
  бейджа сложности нет вообще — там нет понятия сложности как такового.

### Баннер

`achievementsBannerHtml()` (`js/illustrations.js`) — фото-баннер
наверху экрана «Достижения» (`assets/habits/achievements_banner.jpg`).
**Сейчас статичный, не кликабельный** (обычный `<div>`). Кликабельность
с попапом-сводкой добавлялась в одном из заходов и была полностью
откачена по прямой просьбе — сейчас это просто декоративная картинка.

### Праздничная анимация 100% (отдельная функция, не achievement)

Полноэкранный конфетти-оверлей (`js/components/summitCelebration.js`)
срабатывает при достижении 100% горы **в любом разделе приложения**,
но это **не то же самое**, что достижение `summit` выше:

- `summit` в `ACHIEVEMENTS` — разблокируется один раз за всю жизнь
  приложения (one-way ratchet), просто карточка в «Достижениях», без
  анимации.
- Конфетти — срабатывает **раз в календарный месяц**, при первом
  достижении 100% именно в этом месяце (`state.meta.
  summitCelebrationShownMonth`, сравнение с текущим `monthKey`),
  независимо от того, разблокирован ли уже когда-то `summit`.
  Проверка (`checkSummitCelebration()`) вызывается безусловно в
  конце `render()` в `js/app.js` — на любое изменение состояния и
  на любой переход по вкладке, поэтому и срабатывает «в любом
  разделе». Закрывается кликом в любом месте оверлея или сама через
  6 секунд.

## 5. Настройки

**Файл:** `js/views/settingsView.js`.

| Блок | Что делает |
|---|---|
| Оформление → Тема | `light` / `system` / `dark`. Хранится в `meta.settings.theme`, применяется `applyTheme()` (`js/logic/theme.js`) — ставит/убирает `data-theme` на `<html>`; `system` = ничего не ставит, решает `@media (prefers-color-scheme)` в CSS. |
| Привычки → Единица измерения по умолчанию | Подставляется в форму новой числовой привычки (см. раздел 2). Кастомный выпадающий список (не нативный `<select>` — тому нельзя стилизовать попап под зелёный акцент приложения), `meta.settings.defaultUnit`. |
| Уведомления → Напоминания | Только **локальный тестовый пуш** через `Notification` API браузера в момент включения тумблера — приложение без сервера, значит настоящих фоновых push-напоминаний по расписанию нет и быть не может. `meta.settings.notificationsEnabled` — просто флаг, ни на что кроме текста самого себя не влияет. |
| Данные → Экспорт данных | Весь объект `state` целиком как `.json` (`Blob` + программный клик по `<a download>`). Никакой фильтрации/выборки — всё состояние приложения одним файлом. |
| Данные → Сбросить аккаунт | `localStorage.clear()` + `location.reload()`, с подтверждающим диалогом (`openConfirm()`). Необратимо. |
| Обучение → Показать обучение заново | `startOnboarding({ force: true })` — см. раздел 6; запускает тур заново независимо от того, пройден ли он уже. |
| О приложении | Версия (`APP_VERSION = "2.0"`, константа в файле), короткое описание, что данные хранятся только на этом устройстве (localStorage), автор — «Капустин Николай». |

Импорта данных (обратно из экспортированного `.json`) в интерфейсе
нет — только экспорт.

## 6. Обучение (онбординг)

**Файл:** `js/components/onboarding.js`.

### Когда запускается

`startOnboarding()` вызывается один раз при загрузке `js/app.js`,
после первого `render()` (чтобы таббар уже существовал в DOM). Ничего
не делает (`no-op`), если `state.meta.onboardingCompleted === true`.
Повторный запуск — кнопка в Настройках, `startOnboarding({force:
true})`, игнорирует уже пройденный флаг.

### Машина состояний (`active.phase`)

1. **`"welcome"`** — полноэкранный экран сразу при старте: зелёный
   градиент, «Готов покорить вершину?», кнопка «Начать восхождение
   🚀» и ссылка «Пропустить обучение».
2. **`"spotlight"`** — подсветка всей нижней навигации целиком
   (4 полупрозрачные «шторки» вокруг таббара + кольцо), подсказка
   «Нажми на любую вкладку внизу — необязательно по порядку». Прямой
   клик-листенер на каждую вкладку (а не диффинг `location.hash`) —
   иначе клик по уже активной вкладке (если тур стартовал прямо на
   ней) не поймать, поскольку `hashchange` в этом случае не
   срабатывает.
3. **`"roam"`** — свободная навигация без оверлея. При первом заходе
   на любую из 5 вкладок (в **любом** порядке, не навязанном) —
   короткий попап (`openModal()`) с описанием именно этого раздела на
   2-3 предложения (`TAB_INTROS`, свой текст под каждую вкладку —
   Испытания/Привычки/Прогресс/Достижения/Настройки), с кнопками
   «Понятно» и «Пропустить обучение». Повторный заход на уже показанную
   вкладку popup не открывает.
4. **`"completion"`** — как только показаны все 5 вкладок, сразу
   после закрытия последнего попапа — полноэкранное «Готово!» с
   подсказкой, что тур можно перезапустить из Настроек.

### Хранение флага

`state.meta.onboardingCompleted` (`localStorage`, ключ
`"habit-mountain:v1"`) — `true` после explicit skip (с любой из
активных фаз, кроме completion — там уже есть кнопка завершения) или
после нажатия «Отлично!» на финальном экране. Список посещённых
вкладок за текущий проход тура — модульная переменная
(`active.visitedTabs`), не персистится: если пользователь закрыл
приложение на середине тура, при следующем запуске тур начнётся
заново с welcome-экрана (флаг ещё не выставлен).

Миграция для уже существующих сохранений (сделанных до появления
этой фичи) — если поле `onboardingCompleted` вообще отсутствует в
сохранённых данных, оно трактуется как `true` (уже пройдено), а не
`false` — чтобы обновление приложения не показало тур внезапно
старому пользователю. Единственный случай, когда оно реально `false`
— явно сохранённое `false` (недопройденный тур на свежей установке).

## 7. Общая техническая часть

### Хранилище данных

Всё состояние приложения — **один ключ localStorage**,
`"habit-mountain:v1"` (`js/state/storage.js`), никакого бэкенда/сети
не задействовано вообще (кроме опционального шрифта Google Fonts,
некритичного для работы). Форма:

```js
{
  schemaVersion: 2,
  habits: [{ id, name, type, unit, target, color, icon, createdAt, archived }],
  entries: { [habitId]: { [dateKey /* "YYYY-MM-DD" */]: value } },
  meta: {
    unlockedAchievements: {},      // раздел 4
    completedChallenges: {},       // раздел 1
    incompleteChallenges: {},      // раздел 1
    lastSeenMonth: null,           // для recap при смене месяца
    summitCelebrationShownMonth: null, // раздел 3/4 (конфетти)
    onboardingCompleted: false,    // раздел 6
    settings: { theme, notificationsEnabled, defaultUnit }, // раздел 5
  },
}
```

Ключевые особенности реализации:

- `loadState()`/`saveState()` — единственная точка входа/выхода;
  простой pub/sub (`subscribe(fn)`) — любой `saveState()` синхронно
  оповещает всех подписчиков, в первую очередь `js/app.js`'s
  `render()`, что и заставляет весь экран перерисоваться на любое
  изменение.
- `migrate(raw)` — защитная миграция при каждой загрузке: каждое
  поле проверяется по типу отдельно, отсутствующее/битое поле
  заменяется дефолтом из `emptyState()` — старые/повреждённые
  сохранения не роняют приложение, просто теряют то одно конкретное
  поле, которого не было.
- `entries` хранится **бессрочно**, без пагинации, архивации или
  какой-либо очистки старых дат — вся история привычки с момента
  создания живёт в одном плоском объекте (см. раздел 3 про листание
  месяцев: архив = просто чтение той же структуры за нужный месяц).

### Service worker и кэширование

`sw.js` — **cache-first**: при запросе сначала проверяется кэш,
попадание отдаётся мгновенно без обращения к сети вообще (сеть
используется только на промах, с фоновым докладыванием ответа в
кэш). `APP_SHELL` — явный список всех файлов, которые кладутся в
кэш при установке (`install`), `CACHE_NAME` — версионная строка;
старые кэши с другим именем удаляются при `activate`. **Важное
следствие**: правка любого закешируемого файла (любой `.js`/`.css`,
`index.html`) требует бампа `CACHE_NAME`, иначе реальные
установленные PWA-инстансы могут долго не подхватывать изменения —
это единственный механизм инвалидации.

### Известные ограничения и технический долг

- **Ограничение редактирования дней** (см. раздел 2) — можно
  редактировать только сегодня/вчера/позавчера; это ограничение уже
  снова действует (было временно отключено на период наполнения
  тестовых данных, затем возвращено).
- **`.app-toast` (компонент тостов, `js/components/toast.js`) не
  имеет `pointer-events: none` для угасшего (не `.is-visible`)
  состояния** и сидит на `z-index: 200` — выше модалок (`101`).
  Потускневший, но всё ещё не удалённый из DOM тост может неявно
  продолжать перехватывать клики в своей фиксированной области экрана
  (низ по центру, чуть выше таббара), пока его не сменит следующий
  тост. Обнаружено при тестировании конфетти-фичи, не исправлено —
  вне рамок той задачи.
- **Нет синхронизации между устройствами и нет бэкапа** — все данные
  живут только в `localStorage` конкретного браузера на конкретном
  устройстве. Единственный способ перенести данные — «Экспорт
  данных» в Настройках (см. раздел 5); импорта обратно из такого
  файла в интерфейсе не предусмотрено.
- **`entries` растут бессрочно** без какой-либо архивации/очистки
  старых дат — для обычного многолетнего использования трекера
  привычек объём практически незначителен, но принципиально ничего
  не подчищается сейчас и не планируется.
- **Уведомления не настоящие** — см. раздел 5, только
  демонстрационный локальный пуш в момент включения тумблера, без
  реального расписания.
- **Импорта данных нет** — только экспорт (см. выше).
